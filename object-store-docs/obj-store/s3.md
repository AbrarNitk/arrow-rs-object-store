# Amazon S3 Notes

This file is a capability-oriented note for Amazon S3.

It is not a full product manual. It is a compact technical guide focused on the
parts that matter when reading or designing an object-store abstraction like the
Rust `object_store` crate.

## 1. Core Mental Model

S3 is object storage built around:

- buckets
- objects
- keys
- metadata
- optional versions

At the object API level, the core operations you care about are:

- `PutObject`
- `GetObject`
- `HeadObject`
- `CopyObject`
- `DeleteObject`
- `DeleteObjects`
- `ListObjectsV2`
- `ListObjectVersions`
- multipart flow:
  - `CreateMultipartUpload`
  - `UploadPart`
  - `CompleteMultipartUpload`
  - `AbortMultipartUpload`

The full S3 API surface is much larger than that, but those are the object
operations that map most directly to the Rust crate.

## 2. Main Object APIs

### Read

- `GetObject`
- `HeadObject`
- ranged reads via the standard HTTP range model

`HeadObject` is especially important when modeling metadata-only reads because
it returns object metadata without returning the body.

### Write

- `PutObject`
- `CopyObject`
- multipart upload APIs

### List

- `ListObjectsV2`
- `ListObjectVersions`

`ListObjectsV2` is the usual listing API and returns up to 1,000 objects per
request.

### Delete

- `DeleteObject`
- `DeleteObjects` for bulk delete

Bulk delete matters because the Rust `object_store` crate can map
`delete_stream` to an actual provider batch operation here.

## 3. Consistency Model

Modern S3 gives strong read-after-write consistency for:

- `PUT`
- overwrite `PUT`
- `DELETE`
- metadata reads like `HEAD`
- object listing after successful writes

The important object-store implication is:

- writes to a single key are atomic
- after a successful write response, reads and listings reflect the new state

This is one reason the Rust crate can promise atomic object semantics without
adding provider-specific caveats for ordinary S3 object operations.

## 4. Versioning

S3 versioning is bucket-level.

Important points:

- buckets start unversioned
- once versioning is enabled, new object states get unique version IDs
- if you overwrite an object, S3 creates a new current version
- if you delete an object, S3 inserts a delete marker instead of permanently
  removing the current object state
- objects that existed before versioning was enabled have version ID `null`
- versioning can be suspended later, but the bucket does not go back to a truly
  unversioned state

Practical meaning:

- a "path" is not always enough to identify an object state
- path plus version ID is the more exact identity when versioning is enabled

This maps cleanly onto the Rust crate's optional `version` field in
`ObjectMeta` and `GetOptions`.

## 5. ETags In S3

S3 ETags are useful, but they are not a universal content-hash.

Important rules:

- the ETag reflects object content changes, not metadata-only changes
- for single-part `PutObject` / `PostObject` / `CopyObject` uploads using
  plaintext or SSE-S3, the ETag can be an MD5 digest of object data
- for SSE-KMS or SSE-C uploads, the ETag is not an MD5 digest of object data
- for multipart uploads, the ETag is not an MD5 digest of the full object

Design consequence:

- use ETags as version-like object identity for conditional requests
- do not assume an ETag is always a reusable content checksum

If you need stronger integrity guarantees, prefer S3 checksum fields.

## 6. Checksums And Integrity

S3 has first-class checksum support.

Supported checksum algorithms include:

- `CRC64NVME`
- `CRC32`
- `CRC32C`
- `SHA1`
- `SHA256`
- `MD5`

Important points:

- S3 validates upload integrity against supplied checksum values
- checksum values are stored as object metadata
- multipart uploads can use part-level or full-object checksum workflows
- the SDK can compute and attach checksums automatically

If your abstraction needs "content identity", checksum fields are usually a
better source than ETag.

## 7. Conditional Requests

S3 supports HTTP-style conditional semantics through object APIs.

The key conditions for object-store use are:

- `If-Match`
- `If-None-Match`
- `If-Modified-Since`
- `If-Unmodified-Since`

These map well to the Rust crate's `GetOptions`.

On the write side, conditional create/update behavior exists but is more subtle.
The `object_store` crate's S3 backend has explicit logic around conditional put
support because not every S3-compatible environment behaves identically.

## 8. Multipart Upload

Multipart upload is a first-class S3 capability and one of the most important
reasons object-store abstractions must expose more than a simple `put(bytes)`.

Why it exists:

- upload parts independently
- retry failed parts without restarting the full upload
- improve throughput with parallel uploads

Good practical rule:

- multipart is generally worth using for larger objects
- AWS calls out `100 MB` or larger as a best-practice threshold

This lines up with the Rust crate's `put_multipart_opts` and `WriteMultipart`
design.

## 9. Listing Behavior

The practical listing API is `ListObjectsV2`.

Things to remember:

- page size is up to 1,000 objects per request
- listing is prefix-based
- lexicographical key ordering applies for general purpose buckets
- versioned buckets may require `ListObjectVersions` if you care about all
  versions, not just current keys

This is why `object_store::list` is stream-based and why paginated listing is a
separate internal concern.

## 10. Performance And Request-Rate Guidance

S3 automatically scales, but it still publishes practical guidance.

The most commonly cited baseline is:

- at least 3,500 `PUT`/`COPY`/`POST`/`DELETE` requests per second per partitioned
  prefix
- at least 5,500 `GET`/`HEAD` requests per second per partitioned prefix

Other useful operational guidance:

- use parallelization
- use byte-range fetches for large object reads
- retry `503 Slow Down` and transient latency outliers
- there is no limit on the number of prefixes in a bucket

This matters for analytics engines and for range-heavy readers like Parquet
consumers.

## 11. What Matters Most For The Rust `object_store` Crate

From the crate perspective, the S3 features that matter most are:

- strong object-level consistency
- `HEAD` as metadata read
- ranged `GET`
- multipart upload
- bulk delete
- object versioning
- ETag-based conditional behavior
- checksum metadata

That is why the S3 backend in this repository is one of the richer backends.

## 12. Watchouts

- ETag is not always MD5
- multipart uploads change checksum and ETag behavior
- versioning is bucket-level and introduces delete markers
- conditional put behavior can differ across S3-compatible systems
- performance scaling is strong, but sudden spikes can still surface `503 Slow Down`
